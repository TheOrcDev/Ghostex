# GPUI chat transcript inside React Native (proof of concept)

The desktop app's own GPUI chat renderer (`apps/desktop/src/app/native_chat/`) and Rust chat host
(`apps/desktop/src/app/gx_chat/`, on `packages/gx-chat-core`) drawing the chat transcript inside a
React Native (Expo) screen, with a React Native composer below it. One transcript renderer for the
desktop, the web build and the phone, instead of a second one written in React Native.

Research and the decision trail: `docs/2026-09-26/gpui-mobile-transcript/RESEARCH.md` (local).

## Layout

| Path | What it is |
| --- | --- |
| `../../packages/gpui-mobile/chat/` | Crate `ghostex-gpui-mobile-chat`: the desktop's `native_chat/` and `gx_chat/` compiled for phones through symlinks (the `apps/gpui-web` mechanism), transcript-only, plus the host-facing API in `chat/mobile/` (`init`, `open_transcript`, `ChatTranscript::{open_session, set_draft, send_text, dispatch_action, ...}`, events). The crate root is the folder itself (`chat/lib.rs`), for the reason in its header. The Rust workspace (`packages/gpui-mobile/Cargo.toml`) holds both crates so the real app can link them too. |
| `../../packages/gpui-mobile/host/` | Crate `ghostex-gpui-mobile` (`libghostex_gpui_mobile.so` / `.a`): starts GPUI on gpui-mobile's host-driven platform, owns the one window, and speaks a JSON command/event protocol with the app. `src/root.rs` picks the content (`chat_root.rs`, or `demo/` with `content: "demo"`); `src/android/` is the JNI side, `src/ios/` the C ABI side. |
| `app/` | The Expo app (SDK 57, RN 0.86, New Architecture, same versions as `apps/mobile/app`). `src/chat/` is the chat screen (session picker, composer, toasts); `modules/gpui-view/` is the local Expo module: the `GpuiView` native view that hosts the GPUI surface (Android `SurfaceView` or `TextureView`, iOS `UIView`), `start`, `command`, events. `android/` and `ios/` are generated by `expo prebuild` (gitignored). |
| `scripts/` | `build-android.sh`, `run-android.sh`, `dev-endpoint.sh` (and the iOS pair). |
| `../../.dependencies/gpui-mobile/` | Vendored Longbridge gpui-mobile (Apache-2.0 option), the Android and iOS GPUI platforms. Every local change is listed in its `GHOSTEX.md`. |

## Run it (Android)

```bash
# once: bun, cargo-ndk, the Android SDK/NDK (ANDROID_HOME), JDK 17
cd apps/gpui-mobile-poc
./scripts/run-android.sh --release        # builds the library, prebuilds, builds a release APK, installs, launches
# open a session directly (ids as in its zmx name S90-<projectId>-<sessionId>):
adb shell am start -n dev.ghostex.gpuipoc/.MainActivity --es gpuiSession P3f69:G4kar
# on the emulator of this Mac use the host GPU through GLES (its Vulkan path is MoltenVK, which
# fails one GPUI shader); real phones use Vulkan:
adb shell am start -n dev.ghostex.gpuipoc/.MainActivity --es gpuiBackend gles
# the synthetic list the embedding was first proven with:
adb shell am start -n dev.ghostex.gpuipoc/.MainActivity --es gpuiContent demo
```

`dev-endpoint.sh` (run by `run-android.sh`) writes `app/dev-endpoint.json` with this computer's
gxserver URL and token (gitignored, bundled into the APK: development only) and runs
`adb reverse` so `http://127.0.0.1:<port>` on the phone is the computer's gxserver.

## How it fits together

- **One process-lived GPUI thread.** gpui-mobile's host mode runs GPUI on `gpui-main` with its own
  `ALooper`; the Kotlin view only hands over its `Surface`, `MotionEvent`s (each batched history
  sample with its own time) and pause/resume. GPUI and the chat survive Activity recreation,
  surface loss and JS reloads.
- **The chat is the desktop's.** The Rust chat host keeps its own socket to gxserver (`ws://` on the
  same host and port), its drafts in `<filesDir>/chat/client-storage.sqlite3`, and its own
  `gx-chat-core` per chat. The RN composer drives it with `setDraft` / `send` / `action`; the
  transcript reports `summary` (status, working, send gate, queue, the draft the core holds),
  `hostAction` (links, files), `toast`, and every GPUI clipboard write as `copy`.
- **Transcript-only.** `NativeChatView::set_transcript_only` (desktop `native_chat/render.rs`) skips
  the composer and the cards above it; the phone draws those in React Native.

## What was tested (Android emulator, API 35, host GPU through GLES, release build)

- Live chat against gxserver: sending from the RN composer draws the optimistic bubble at once, the
  composer shows Working and Stop, the reply streams in; markdown, tables, syntax-highlighted code,
  tool rows ("Worked for 8s" expanding to the Bash row, its Command and Result), file changes.
- Touch: drags, flings (about 60 fps, 3 to 4 ms of GPUI work per frame on a long real
  transcript), taps that expand rows without firing during a scroll, the scroll-to-bottom pill,
  long press text selection with drag handles and a Copy / Select All bar (GPUI Kit), copy reaching
  Android's clipboard.
- Keyboard open and close (the GPUI view shrinks and grows; no stale frame), background and
  foreground (surface released and re-attached, a reply that arrived meanwhile is drawn), the
  session picker switching chats.
- Rendering at phone width: the desktop renderer needed no layout change; the touch wording of the
  core's placeholder and no keyboard-shortcut hints are the phone's settings.

## Known gaps before this ships

- **Hover and right-click.** Message actions, table tools (copy as MD/CSV, expand), tooltips and
  the transcript and link menus are hover or right-press on the desktop; on touch they need a tap or
  long-press form (the RN chat's long-press sheet is the reference).
- **Child windows.** The image viewer, table preview, menus and the rewind dialog open separate
  windows on the desktop; the phone platform has one surface, so these need in-surface overlays or
  React Native sheets.
- **Size.** The arm64 library is 62 MB (24 MB gzipped; the APK, which stores it uncompressed, is
  84 MB). Code colouring is limited to Bash, Rust, TypeScript, JavaScript, Python, JSON and diff
  (a user decision; all 35 desktop grammars made it 95 MB). About 10 MB is embedded fonts (the
  Nerd Font mono faces) and 14 MB is symbol names kept for readable backtraces.
- **Accessibility.** GPUI's AccessKit tree is not bridged to TalkBack or VoiceOver yet.
- **minSdk 26** for the library (the real app is at 24).
- **Emulator GPU.** This Mac's emulator runs GLES only; nothing has run on a real phone's Vulkan
  driver yet.

## Moving it into the real app

The real app (`apps/mobile/app`) already has an SSH port forward that listens on the phone's
loopback (`modules/ghostex-native/.../GhostexPortForward.kt`), so the same Rust chat host can reach
the computer's gxserver there the way it does through `adb reverse` here (the desktop's remote
chats do the same through their tunnels). That makes the port: the GPUI view and the Rust chat
host replace the RN transcript and the TypeScript chat host (`src/chat/rust/`), linked into the one
phone library `docs/2026-09-25/mobile-gx-core/PLAN.md` already plans, with the RN composer and
card band driven by the same commands and events as here.
